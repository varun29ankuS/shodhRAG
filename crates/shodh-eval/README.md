# shodh-eval

Measures shodh's retrieval and grounded answers on the real code paths:
folders are indexed with `indexing::index_folder` into a fresh, temporary
index; questions are searched with `RAGEngine::search_comprehensive` (what the
agent's `search_documents` tool calls); answers come from an omp agent session
with the library's document tools and the grounding verifier, as in the app.

## Datasets

JSON files of cases (see `src/dataset.rs`):

```json
{ "id": "msa-notice", "question": "How much notice ends the agreement for convenience?",
  "sources": [{ "file": "contracts/msa.pdf", "pages": [3], "passage": "ninety (90) days written notice" }],
  "facts": ["90 days"] }
{ "id": "none-ceo", "question": "Who is the CEO of Saffron Estates?", "answerable": false }
```

`file` is relative to the corpus folder. `"keep": false` drops a case.

## Committed corpus

`data/synthetic/` holds a synthetic corpus (fictional contracts and invoices as
paged PDFs with tables, research notes with Markdown tables, plain-text
policies; every name and number is invented) and 50 cases, 5 of them
unanswerable. It is generated by `src/synth.rs`; a unit test fails if the
committed files differ from the generator. Regenerate after changing it:

```
shodh-eval synth --out crates/shodh-eval/data/synthetic
```

No third-party texts are included.

## Scanned corpus

`data/scanned/` measures OCR through the same indexing path. Ten pages of the
synthetic contracts and invoices are drawn as images, as a scanner delivers
them (image-only PDFs, no text layer), plus one page as a PNG: 150, 200 and
300 dpi, grey and black-and-white, skewed by up to 2 degrees, some speckled,
three of them invoice tables. Five text files of the synthetic corpus are
copied in as distractors. The 29 answerable cases are the synthetic cases
whose pages were scanned, each with a one-line passage (a table cell's row
for the four table questions), so `passage_hit` measures whether OCR read
the evidence; the 5 unanswerable cases are kept. `ground-truth.json` holds
each scanned file's text by page.

Pages are drawn with Liberation Sans (`data/fonts`, SIL Open Font License
1.1, see `LICENSE-LiberationSans.txt`), not the machine's fonts, and noise
comes from a seeded generator, so the files are reproducible; a unit test
fails if the committed files differ from the generator. Regenerate after
changing it:

```
shodh-eval synth-scanned --out crates/shodh-eval/data/scanned
```

`shodh-eval ocr` reads the scanned files with one engine and scores the text
against the ground truth per page (`line_recall`: lines found whole;
`word_recall`; `cer`: character error rate), with time per page and the
process's memory (Windows). It compares engines, model tiers
(`--ocr-model <dir>` with `det.onnx`, `det.yml`, `rec.onnx`, `rec.yml`),
render resolutions (`--dpi`), detector band sizes (`--det-band-pixels`) and
ONNX Runtime threads (`--threads`, default half the logical cores); `--worker`
reads in the OCR child process as the app does (the child loads the model
with the default settings, so `--threads` does not apply, and the memory
reported is the parent's):

```
shodh-eval ocr --corpus crates/shodh-eval/data/scanned/corpus \
  --truth crates/shodh-eval/data/scanned/ground-truth.json --engine ppocr --models <dir>
shodh-eval ocr ... --engine system [--dpi 300]
```

Measured on this corpus (Windows, 12 threads; PP-OCRv6 small at 300 dpi;
times from an optimised build):

| | Windows OCR (96 dpi) | Windows OCR (300 dpi) | PP-OCRv6 small |
|---|---|---|---|
| passage_hit@1 / @10 | 0.593 / 0.667 | 0.630 / 0.704 | 0.889 / 1.000 |
| page_hit@1 | 0.920 | 0.920 | 0.880 |
| hit@1 / mrr | 0.926 / 0.963 | 0.926 / 0.963 | 0.963 / 0.981 |
| line recall / CER (`ocr`) | 0.744 / 0.111 | 0.773 / 0.106 | 0.955 / 0.0007 |
| time per page | 0.13 s | 0.35 s | 6.2 s |
| peak memory | 160 MB | 357 MB | 349 MB |

PP-OCRv6 reads tables row by row and survives speckle; Windows OCR's misses
are mostly table rows read out of order. PP-OCRv6 is the default on Windows
and macOS (`OcrEngineChoice::Auto`) by decision, knowing that page_hit@1 is
one question lower and a page takes seconds.

So that OCR does not make the machine feel heavy, it runs on half the
logical cores, below normal priority, without spinning between operators,
and in the app in a child process. The same 11 pages (release build, 12
logical cores; time per page, CPU time of the whole run, peak working set):

| | s/page | CPU s (11 pages) | peak memory |
|---|---|---|---|
| before: 12 threads, normal priority, spinning | 4.5-4.7 | 227 | 344-361 MB |
| 12 threads, below normal, no spinning | 4.7 | 232 | 344 MB |
| default now: 6 threads, below normal, no spinning | 5.5-5.6 | 197-202 | 340-358 MB |
| 2 threads (a 4-core CI runner) | 9.5 | 178 | 342 MB |
| default, in the OCR child (`--worker`) | 5.5 | 200 (child) | 342 MB child, 12 MB parent |

Per-page line recall, word recall and CER are identical at 2, 6 and 12
threads, and the scanned baseline holds unchanged.

## Paper corpus

`data/papers/` is a synthetic research library of 21 papers and 12 reading
notes (33 files), for the questions researchers ask of their own papers. Seven papers
are hand-written in `src/papers_text.rs`: six preprint-style PDFs (title,
authors, numbered sections, display equations, tables, figure captions,
bibliography, running headers) and one LaTeX source. Fourteen are generated
by `src/papers_gen.rs` around hand-written anchor sentences: twelve method
papers in six topics, a thesis and a survey of KV cache compression. Their
remaining text comes from per-topic vocabularies and sentence templates, drawn
with a seeded generator. Three papers are long (two surveys and the thesis),
and they share the other papers' vocabulary. Twelve reading notes (two per
topic, generated text only) make the library larger than a 50-candidate pool
holds at two candidates per file. The library is several times larger than
the pool a search reranks at `k = 10`, the condition under which long papers
crowd the others out, and has more files than the pool, the condition under
which a per-file pool limit could crowd out the chunks a question about one
paper needs.

The 82 answerable questions cover definitions and mechanisms, equations,
tables and figures, "which paper ..." questions (answered by the paper, not by
the works that cite it), a citation question, and 15 questions that need 2 to
4 papers. Among them is `multi-long-context-memory`, a broad question that
once returned passages from only two files. Depth questions (17) ask about
one paper in detail and list three of its passages, in three different
sections and so in three different chunks. There are also 6 unanswerable
questions. A case names its files and passages; the page is found by laying
out the paper. Every method, author, benchmark and number is invented, and
unit tests check that the committed files are the generator's output, that
every passage is on exactly one page of its paper and in no file the case
does not list, that every fact is in its sources, that no other file
holds a key fact (a number, or a phrase of several words), and that the
layout parser puts every PDF passage on its page (the synthetic set is checked
the same way). Regenerate after changing the generator:

```
shodh-eval synth-papers --out crates/shodh-eval/data/papers
```

## Commands

```
shodh-eval models    --models <dir>                       # pinned E5 + reranker + OCR (+ --answer-check: NLI model)
shodh-eval retrieval --corpus <dir> --models <dir> --dataset <file> [--runs 3] [--k 10]
                     [--ocr auto|system|ppocr] [--ocr-dpi <n>] [--system-ocr-dpi <n>]
                     [--search key=value,...]
shodh-eval ocr       --corpus <dir> --truth <file> --engine ppocr|system [--models <dir>]
                     [--threads <n>] [--worker]
shodh-eval compare   --baseline <file> --report <dir>/retrieval-report.json
shodh-eval generate  --corpus <your folder> --models <dir> --n 50
shodh-eval answers   --corpus <dir> --models <dir> --dataset <file> [--limit 10]
```

Outputs (`*-report.json`, `*-summary.md`, generated `questions.json`) go to
`.eval-local/runs/<folder>-<hash>/` unless `--out` is given; every output
folder gets a `.gitignore` of `*`. Questions, answers and reports about your
own folders stay there and are never committed.

**Retrieval metrics** (no LLM): `hit@1/5/10` and `mrr` over distinct
documents (a document counts once, at its first chunk), `page_hit@k` (a chunk
of an expected file on an expected page), `passage_hit@k` (a chunk containing
the expected passage), `recall@5/10` (the share of a case's expected documents
among its first k documents) and `ndcg@10` (binary relevance per expected
document), the same over the cases that expect several documents
(`multi_recall@k`, `multi_ndcg@10`), `multi_files@10` (distinct files among
the first 10 results of those cases), `depth_recall@10` (the share of a
depth question's passages held by its first 10 results; a case is a depth
question when it lists three passages or more), `recall@20` and
`depth_recall@20` (from a second search with 20 results, the most the agent's
tool asks for), and `ingest_ok` (files indexed / files seen).

Reported, never gated: search latency p50/p95, and diagnostics. The
diagnostics are the distinct files among the first 10 and 20 results, and how
many results and files each search stage keeps (`vector`, `candidates`,
`content`, `thresholded`, `pooled`, `returned`; from
`RAGEngine::search_traced`).
`passage_not_in_index` is the share of cases whose passage is in no stored
chunk of its document, which means it was lost in parsing or chunking rather
than in ranking; such a case also records the stored chunk nearest to it.
More files is not better for a question one document answers, so only the
multi-document cases' file count is gated.

`--search` measures engine settings before their defaults change:
`rrf_k`, `candidate_multiplier`, `min_score_threshold`, `score_weight`,
`source_decay`, `pool_source_cap`, `pool_open_share`, `reranking` (`on`/`off`) and
`chunk_max_tokens`, for example `--search pool_source_cap=3,source_decay=0.7`.

The per-file pool limit (`pool_source_cap`, with `pool_open_share` for the
part of the pool filled in score order first) is off by default. On the paper
library every limit tried, 2 to 4 per file and with 0 to 70% of the pool
open, raised `multi_recall@10` (0.711 to 0.756-0.789) and `multi_files@10`.
Every one also lowered `depth_recall@20` (0.869 to 0.837-0.853), and a limit
of 2 with no open part lowered `passage_hit@10` too. Fewer chunks of one
paper reached the reranker. Measure a new pool policy with `--search` on all
three sets before changing the default.

**Answer metrics** (opt-in; never in CI): `fact_recall`, `citation_correct`
(stated facts found in a passage the answer cites), `cited_expected_source`,
`claims_supported` and `flagged_per_answer` (the grounding verifier's
verdicts), `refusal_correct` on unanswerable cases, `false_refusal`,
`answered`, and `evidence_seen` (a passage the answer could cite, searched or
read with `open_document`, holds the expected passage; each case also records
the passage's rank in the first search that returned it). Refusals are
detected by phrase; the report says which answers were scored how. Latency is
per answer from starting the agent session; time to first token is from
sending the question to the first streamed text. A rate-limited question is
asked again after 20, 40, 80 and 160 s (or the provider's own hint), and the
run stops when the provider's quota is used up: the remaining questions are
not asked and that question is left out of the metrics. Provider errors are
counted by kind in the report.

## Language model (answers, generate)

Chosen with environment variables only; the eval never reads the app's
settings or key store:

```
SHODH_EVAL_PROVIDER=anthropic|openai|openrouter|google|xai|ollama|lm-studio
SHODH_EVAL_MODEL=<model id>
ANTHROPIC_API_KEY / OPENAI_API_KEY / OPENROUTER_API_KEY / GEMINI_API_KEY / XAI_API_KEY
```

Both commands send corpus passages to that model; use a local provider for
folders whose content must not leave the computer. `answers` downloads the
pinned agent runtime into `.eval-local/runtime` on first use (or set
`SHODH_OMP_PATH`). It differs from the app in what is not there: no app tools
(calendar, web, memory), no table refinement, no citation-graph ranking.

## Baseline and CI gate

`data/synthetic/baseline.json` is the committed corpus's retrieval baseline,
recorded from 3 fresh runs:

```
shodh-eval retrieval --corpus crates/shodh-eval/data/synthetic/corpus \
  --dataset crates/shodh-eval/data/synthetic/dataset.json --models <dir> --runs 3 \
  --write-baseline crates/shodh-eval/data/synthetic/baseline.json
```

`compare` fails when the dataset, the corpus or an engine setting changed
(the number of runs excepted), a metric is missing, or a metric is below
`mean - max(3 * stddev, 1e-9)`. Retrieval is deterministic
(stddev 0), so any drop fails. A change that improves retrieval, or changes
the corpus or dataset, records a new baseline in the same PR. The `Retrieval
eval` CI job runs this on every PR.

`data/scanned/baseline.json` is the scanned corpus's baseline, read with
PP-OCRv6 (`--ocr ppocr` fails when the OCR model is not installed, so the
gate never measures another engine):

```
shodh-eval retrieval --corpus crates/shodh-eval/data/scanned/corpus \
  --dataset crates/shodh-eval/data/scanned/dataset.json --models <dir> --ocr ppocr \
  --runs 3 --write-baseline crates/shodh-eval/data/scanned/baseline.json
```

The same job gates it after the synthetic corpus, and then the paper
corpus against `data/papers/baseline.json`. `--ocr system` measures
Windows OCR on the same files (`--system-ocr-dpi` renders its pages at a
chosen resolution instead of 96 dpi).
